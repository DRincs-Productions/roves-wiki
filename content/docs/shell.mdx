## What the Shell is

The Shell is **the heart of Roves** — the actual compiled engine binary. Everything else on
this wiki (<DynamicLink href="/docs/packmaster">Packmaster</DynamicLink>,
<DynamicLink href="/docs/action">the GitHub Action</DynamicLink>) doesn't replace it — both
just build or download this exact same Shell on your behalf and hand you the result already
put together.

As the name suggests, the Shell is a **container**: an empty, pre-built native application
that knows how to load and run a *dist* — your game's already-built web output, whatever
your own bundler (Vite, webpack, or anything else that produces a browser-runnable
`index.html`) produces — as a real, double-click desktop app. No browser chrome, no toolbar,
no address bar — one window that opens your game and nothing else. It's the same role a
Tauri or Electron shell plays, just for a different underlying engine; see
<DynamicLink href="/docs/getting-started/why">Why Roves?</DynamicLink> for that comparison.

## The Shell is already built for you

You don't need to compile anything to get a working Shell. Every tagged engine version
publishes a ready-to-run Shell — with no game content in it yet — on the
[Releases page](https://github.com/DRincs-Productions/roves/releases), starting at
`v0.1.0`. Each platform is published **twice**: a plain build and a `_steam`-suffixed one
compiled with the <DynamicLink href="/docs/integrations/steam">Steam bridge</DynamicLink>
built in.

| Platform | Download | Contains |
| --- | --- | --- |
| Windows | `roves_shell_windows.zip` / `_steam.zip` | `play.exe` + the DLLs (incl. GStreamer's) it needs |
| macOS | `roves_shell_macos.zip` / `_steam.zip` | `play.app`, whose `Contents/MacOS/play` *is* the engine binary |
| Linux | `roves_shell_linux.zip` / `_steam.zip` | `play` (expects GStreamer already installed via your distro) |

These are optimized (`--release`) builds with the real GStreamer media stack (bundled
automatically on Windows/macOS). Pick the version your game targets, download the zip for
your platform, and extract it anywhere — that's the whole install step.

## Inserting your dist into the Shell

This is the part that actually matters: turning that empty container plus your built game
into something playable. Every path below — Packmaster included — ends up doing the exact
same thing under the hood, so pick whichever fits how you work.

Nothing here requires Rust, Python, or `mach` — just a downloaded Shell and your already-built
game.

1. **Build your game** with your own bundler, however you already do it. This produces a
   folder — commonly named `dist/` — containing an `index.html` plus whatever assets it
   references.
2. **Download and extract** the matching Shell zip from the table above.
3. **Copy your build output next to the Shell binary** (`play.exe` / `play.app` /
   `play`), keeping it named `dist` so it lines up with the Shell's own default expectations.
4. **Tell the Shell where to find it.** Two ways, depending on whether you want a
   double-click-runnable copy or you're just testing:

   - **A `launch.json` next to the binary** (recommended — this is exactly what
     `mach bundle`/Packmaster generate for you):

     ```json title="launch.json"
     {
       "url": "dist/index.html"
     }
     ```

     With this file in place, double-clicking the Shell binary opens your game directly —
     no arguments needed. This is what actually makes the container double-click-runnable.

   - **Pass the path as an argument**, for a quick check without creating any file:

     ```bash title="from a terminal, or a shortcut's target"
     ./play dist/index.html
     ```

     Any argument on the command line skips `launch.json` entirely, so use this for testing,
     not for what you hand to a player.

<Callout title="No launch.json and no argument? The Shell isn't broken">
Without either, the container has nothing to run — it just opens the stock Servo homepage.
That's expected: it means no dist has been pointed at it yet, not that something failed.
</Callout>

<Callout title="This covers loose files only" type="warn">
Hand-writing `launch.json` this way ships your dist as plain, individually browsable files
(equivalent to `mach bundle --content-compress=none`). The compressed tar+zstd packing
described in <DynamicLink href="/docs/integrations/content-packing">Content packing</DynamicLink>
is produced by `roves-content-packer`, invoked either through `mach bundle` or by Packmaster
linking that same crate as a library — there's no manual equivalent for that path.
</Callout>

`launch.json` also accepts `window_size` and extra `args` — see the flags table further down
for what each corresponds to; a hand-written file only needs `url` to work.

## Building the Shell yourself

This is the **least important section for most people**. You only need this if you're
working on Roves itself, need a flag Packmaster doesn't expose, or want to understand what's
actually happening underneath the paths above.

Roves' Shell is not a from-scratch engine — it's a vendored, customized fork of
[Servo](https://servo.org), built with Servo's own `mach` tooling. Every customization on top
of stock Servo (no browser chrome, the single-executable bundle, the boot splash, the
`roves:` protocol bridge, optional Steam) is tracked, file by file, in
[`CUSTOMIZATIONS.md`](https://github.com/DRincs-Productions/roves/blob/main/CUSTOMIZATIONS.md).

```bash
git clone https://github.com/DRincs-Productions/roves
cd roves
```

<Accordions>

<Accordion title="Prerequisites" id="prerequisites">

Roves builds exactly like upstream Servo, using the same `mach` tooling — see the
[Servo wiki](https://servo.org) for the authoritative, up-to-date build documentation. This
only calls out the parts specific to working in *this* repo.

**Rust** — the exact toolchain version is pinned in `rust-toolchain.toml` at the repo root;
`rustup` picks it up automatically once you `cd` into the repo, no manual version selection
needed.

**Python 3.11+** — Servo's `mach` tooling needs it. A couple of Python standard-library
additions used by `python/mach`/`python/tidy` (`contextlib.chdir`, `typing.LiteralString`)
simply don't exist on 3.10 — `mach` fails importing its own commands, not just warns, on an
older interpreter. The repo expects [`uv`](https://github.com/astral-sh/uv) to provision the
right Python version automatically; without it, `mach` falls back to whatever `python3`
resolves to on `PATH`, a real, easy-to-hit gap on Linux distros that still default to 3.10.

**Platform build dependencies** — run `./mach bootstrap` first; it installs the
platform-specific system packages the build needs (a C/C++ toolchain, `libclang`, and a
handful of media/graphics libraries). A `bindgen`/`libclang` error usually means you skipped
this. Gamepad support (`gamepad`, on by default) is built on [SDL3](https://libsdl.org/),
compiled from vendored source as part of the normal build (`cmake` + your C/C++ toolchain —
no separate system SDL3 install needed); on Linux, missing X11/Wayland/ALSA/udev development
headers can make that step skip individual SDL3 subsystems rather than fail outright, which is
one reason to still run `./mach bootstrap` first rather than jump straight to `./mach build`.
CI creates an SDL3 virtual gamepad on macOS, Windows and Linux, then checks connection, axis and
button input, and disconnection with a 90-second runtime limit. The desktop smoke tests also
launch the real Shell with an SDL virtual gamepad and check that its button presses reach the
page through the Web Gamepad API.

**Known issue in Shell releases up to and including `v0.5.1`:** controllers were silently ignored
on every platform. The gamepad subsystem tried to open a second SDL event pump, which SDL
doesn't allow, and button updates used SDL's device IDs instead of the page's
`navigator.getGamepads()` index. A controller connected before the game's page finished loading
was also never announced to that page. All three are fixed in Shell `v0.5.2`.

On macOS, gamepad support stays **off by default**: SDL3's gamepad initialization once hung the
Shell there. Since Shell `v0.5.2` you can opt in at runtime, without a special build, by
launching with `ROVES_MACOS_GAMEPAD=1`. Only
the exact value `1` enables it, and CI exercises that path on a macOS runner with a virtual
controller. A physical controller on a real Mac has not been verified yet, so treat it as
experimental and don't turn it on for players.

`ROVES_TEST_VIRTUAL_GAMEPAD=1` is a CI-only switch that makes the Shell attach and keep pressing
a virtual SDL gamepad for about a minute. Never set it in a shipped game.

**JavaScript engine: V8** - Since Shell `v0.7.0`, games run on V8, the JavaScript engine of
Chrome, instead of SpiderMonkey. Your game code needs no changes. PixiJS, Three.js, Phaser and
similar libraries only depend on standard JavaScript and Web APIs, and they are checked on every
engine change. A few things to know:
- **WebAssembly** works, including `WebAssembly.instantiateStreaming` on a fetched `.wasm` file.
- **JIT-less builds** (V8 without its just-in-time compiler, the mode meant for platforms that
  forbid generating code at runtime) have **no WebAssembly**. Unity, Godot or Emscripten exports
  need a regular build.
- **Developer-tools JavaScript debugging** (breakpoints, stepping) is not available yet on V8.
  `console` output works as before.
- A page you leave by navigating is not freed until the game quits. Single-page games, which is
  most of them, are not affected.

If something that worked on an earlier Shell behaves differently on `v0.7.0`, please report it
with the smallest page that shows it.
Engine contributors should read
the shared [AGENTS.md instructions](https://github.com/DRincs-Productions/roves/blob/main/AGENTS.md).

**Disk space and RAM** — Servo bundles SpiderMonkey (the JS engine, compiled from C++) and
ANGLE (GL-over-native graphics translation). A clean build compiles a lot of C++ on top of
the Rust — budget real disk space for `target/`, and enough RAM that a fully parallel build
doesn't thrash (`cargo build -j <n>` with a lower job count trades build time for peak
memory if you're constrained).

</Accordion>

### Build and bundle

```bash title="from the repo root"
./mach bootstrap
./mach build --release
```

Add `--features steam` if you need the <DynamicLink href="/docs/integrations/steam">Steam
bridge</DynamicLink> compiled in.

`--features mimalloc` (since `v0.5.2`, experimental) swaps the global memory allocator for
[mimalloc](https://github.com/microsoft/mimalloc). By default Windows uses the system allocator
and macOS/Linux use jemalloc. It exists for allocator A/B measurements and has not been shown to
be faster yet, so don't ship it in a game unless your own measurements say it helps. The
`perf-ab` pre-release on the Roves repository publishes a Windows build of each for comparison.

```bash
./mach bundle --content-dir path/to/dist --output release
```

`mach bundle` is what turns that build plus your dist into the container described above,
producing exactly the same `launch.json`-driven layout — no separate launcher process, no
`roves-content-packer` binary shipped alongside it (packed-content extraction happens
in-process, inside the engine binary itself, which already links that crate as a library):

| Platform | Portable output |
| --- | --- |
| Windows | `play.exe` next to a handful of DLLs it needs directly, with GStreamer's plugin DLLs (and their own private codec dependencies) tucked into a `lib/` subfolder |
| macOS | `play.app`, whose `Contents/MacOS/play` *is* the engine binary |
| Linux | `play` |

### Flags

| Flag | Default | Description |
| --- | --- | --- |
| `--content-dir <dir>` | — | Web content to copy/pack into the bundle. |
| `--html-file <path>` | `dist/index.html` | Entry HTML file, relative to the bundle root. |
| `--output`, `-o <dir>` | `<build dir>/bundle` | Where to write the bundle. |
| `--window-size <WxH>` | `1280x720` | Initial window size in logical pixels. |
| `--diagnostic-script` | off | Ship a `diagnose.bat`/`diagnose.sh` next to the binary that launches the game from a console and prints its exit code plus `roves.log` inline. See <DynamicLink href="/docs/integrations/diagnostics">Diagnostics</DynamicLink>. |
| *(trailing args)* | — | Anything else is forwarded verbatim to the running game as CLI args (written into `launch.json`). |

### Performance diagnostics

Shell releases since `v0.5.1` expose an
opt-in counter stream for comparing idle and animated workloads without changing the game.
Set `ROVES_PERF_LOG_INTERVAL_MS` to a positive reporting interval before launching the Shell:

```bash
ROVES_PERF_LOG_INTERVAL_MS=10000 ./play dist/index.html
```

The normal `roves.log` receives aggregate `[roves-perf]` lines with real SDL events versus
wait timeouts, redraws queued or coalesced, dispatched redraws, WebView paints, egui
runs/tessellations/paints, framebuffer blits, composed or direct presents, and final window
presents. The counters are disabled by default and create no sampling timer or background thread.

Each interval also emits one `[roves-perf-time]` line with the total and worst-case wall-clock
time, in microseconds, of four shell phases: `webview_paint` (Servo/WebRender painting the
page), `egui_run` (the egui update pass), `shell_paint` (the off-screen blit plus any egui
painting) and `present` (the final window swap). Divide a total by the matching count from the
`[roves-perf]` line for a per-frame average. GL work is asynchronous, so GPU cost usually shows
up in whichever phase waits on it, typically `present` under VSync; the times are CPU-side and
not a GPU profiler.

For meaningful Roves/Chrome comparisons, keep the
page, release build, window size, warm-up and sample duration identical; do not treat results
from a debug build as representative.

Since Shell `v0.7.2`, two more aids work on a game you have already bundled:
- **`ROVES_EXTRA_ARGS`** appends engine options to the launch of a bundled game, which otherwise
  ignores the command line. For example, `ROVES_EXTRA_ARGS="-p 5"` prints the engine's own time
  profile every 5 seconds, split into script, layout, painting and so on.
- **`ROVES_V8_FLAGS`** passes extra options to the JavaScript engine, V8 (since Shell `v0.7.8`).
  It is meant for diagnosing garbage-collection pauses together with the `[roves-gc]` lines.
- **`[roves-gc]` lines** appear in `roves.log` whenever a JavaScript garbage collection pauses
  the game for 8 ms or more, with the JavaScript heap size at that moment. Frequent long pauses
  point at a game that allocates a lot per frame.

### Shader cache

Since Shell `v0.7.8`, the graphics shaders compiled for your game are saved in the game's
settings folder and reused on the next launch, like Chrome's GPU shader cache. The first launch
compiles them when they are first needed; later launches avoid those stalls. The cache is rebuilt
automatically after a graphics driver update.

### Minimized or covered window

Since Shell `v0.7.8`, the Shell behaves like Chrome when the game window is minimized, hidden or
completely covered by other windows. `document.visibilityState` becomes `hidden` and a
`visibilitychange` event fires, and timers and animations slow down to save CPU and GPU.
Everything resumes when the window is visible again. Listen for `visibilitychange` to pause your
music, as you would in a browser.

### Downloaded assets are cached on disk

Since Shell `v0.7.7`, images, audio and other files your game downloads from the internet are
saved in a disk cache in the game's own data folder. They are reused on later launches for as
long as the server's caching headers (`Cache-Control`, `Expires`) allow, so set a sensible
`max-age` on your asset host. Files are never cached when the request carries cookies or an
`Authorization` header. Each game also has its own settings folder, next to its `roves.log`.

### Graphics card

Since Shell `v0.7.5`, on Windows laptops with both an integrated and a dedicated GPU (NVIDIA
Optimus, AMD switchable graphics), games run on the dedicated GPU by default. The driver control
panel can still override this per game. WebXR (VR/AR) is not available in the Shell.

### Direct presentation

The development tree caches actual WebGL drawing-buffer dimensions until the next canvas
resize, avoiding repeated synchronous queries from JavaScript to the WebGL thread. This is
not yet a released performance claim. Benchmark the same production page and dimensions in
Roves and Chrome; GPU usage must be measured per process. Web Animations playback remains
incomplete and disabled, and AudioWorklet is not implemented, so loading motion or Tone.js
alone does not establish full compatibility. Current measurements are maintained in the
engine repository's [`docs/ROVES_PERFORMANCE.md`](https://github.com/DRincs-Productions/roves/blob/main/docs/ROVES_PERFORMANCE.md).

Web Audio frequency analysis in the development tree uses RealFFT/RustFFT instead of a
quadratic direct transform. It preserves the Blackman window, Web Audio normalization and
smoothing and reuses FFT buffers. This benefits `AnalyserNode` frequency reads; it does not
add AudioWorklet support or imply that every Tone.js operation becomes faster.
The development analyser transport uses a bounded Crossbeam ArrayQueue to retain the latest
32768 samples and import them when JavaScript reads analysis data. It removes the per-block
DOM tasks and their rooted DOM callback. Whole-game CPU savings remain to be measured;
this change is not yet a versioned release. Audio graph processing and downmix still run.
Commit `605d486b079` passed the ordered patch validation and all desktop, Windows, macOS,
Linux, Android, and iOS CI jobs ([desktop workflow](https://github.com/DRincs-Productions/roves/actions/runs/38952244417)).
Chrome DevTools MCP verified the transport fixture with eight analyzers both unread and read
at about 60 Hz. Those are functional checks only; the post-change Roves runtime has not yet
been verified, and no CPU comparison is claimed.
Animation comparison fixtures disable the background panels' FPS polling. The Three.js
diagnostic panel disposes geometry/material and removes its canvas on unmount. Re-run both
browser baselines with the same corrected page; fixture savings are not engine speedups.

On October 17, Chrome DevTools MCP observed 1–120 native animations on the typewriter fixture
over ten seconds, using opacity and transform (Chrome 155.0.8059.84, visible, 1024×740,
DPR 1). Roves uses the JavaScript fallback while Web Animations playback is incomplete.
This supports prioritizing the native animation path; it does not measure its potential CPU
savings or explain every long frame.
WebRender's dynamic property API is already used for caret colors; animated opacity and
transform bindings remain to be integrated. Playback support and compositor integration
both need verification before claiming that these animations avoid scene rebuilds.

Optimized Windows builds from commit `20f899dcfbb` pass numerical CI checks and local WebGL
resize/readback and audio spectrum checks. In matched headless API tests, spectrum reads at
2048/8192 samples dropped from about 27/432 ms to 0.03/0.09 ms. These are individual API
measurements, not whole-game CPU, GPU or RAM results; the engine performance notes include
the reproduction pages, sample counts and limitations. The experimental `perf-ab` builds
are separate from the versioned shell consumed by Packmaster and roves-action.

Since Shell `v0.7.4`, when a game fills the window and no Shell dialog, status overlay or
accessibility tool is active, the Shell copies the game's frame straight to the window instead
of drawing it through its own interface layer. Anything else (a dialog, the boot splash, an
error page) automatically uses the full path for that frame. Nothing needs to be configured:
the earlier `ROVES_DIRECT_PRESENT` variable is no longer read. With the performance counters
on, direct frames show up as `direct_presents` and the others as `composited_presents`.

### Custom game icon

| Flag | Default | Description |
| --- | --- | --- |
| `--icon-png <path>` | auto-detect | Window/taskbar icon (PNG), applied after packaging — no compile needed, works for a prebuilt shell too. Not supported on macOS yet (its own Dock/app icon has no runtime override). |
| `--icon-ico <path>` | auto-detect | Windows-only `.exe` icon (multi-size `.ico`), patched into the bundled `play.exe` in place via `rcedit`. |

"Auto-detect" means: with neither flag given, `mach bundle` looks for an `icon.png`/`icon.ico`
sitting directly in `--content-dir` before falling back to Roves' own branding — many
bundlers already emit one there for their own PWA manifest, so a game that already has one
gets its own icon for free, no flag needed. Pass either flag explicitly to override this.

### Content packing

How `--content-dir` gets packed into the bundle — see
<DynamicLink href="/docs/integrations/content-packing">Content packing</DynamicLink> for the
full design (why, the boot-set/lazy-extraction split, the archive layout). These flags tune
or disable it:

| Flag | Default | Description |
| --- | --- | --- |
| `--content-compress` | `auto` | `auto`: pack into a handful of tar+zstd archives. `none`: copy in as loose, individually browsable files. |
| `--content-compression-level` | `1` | zstd level for `--content-compress=auto`. Low by default — speed over ratio. |
| `--content-max-pack-size` | `500M` | Split archives so none exceeds this size. |
| `--content-exclude <glob>` | — | Repeatable. Leave matching files as loose, uncompressed files (e.g. a save-data folder that shouldn't sit inside a read-only archive). |
| `--content-boot-include <glob>` | — | Repeatable. Extra files eagerly extracted at boot, beyond the html file, whatever it directly references and every JavaScript/CSS file (always extracted at boot since Shell `v0.7.6`). |

### Distributing installers

Each platform also has one installable alternative to the portable output above, wrapping
the exact same staged files — nothing extra is left behind once the installer is built:

| Platform | Installer flag | Produces |
| --- | --- | --- |
| Windows | `--msi` | An installable `.msi` |
| macOS | `--dmg` | `play.app` wrapped in an installable `.dmg` |
| Linux | `--deb` | An installable `.deb` |

| Flag | Default | Description |
| --- | --- | --- |
| `--package-name <name>` | `roves` | Package name for `--deb`/`--msi`/`--dmg`. |
| `--package-version <ver>` | `0.0.0` | Package version for `--deb`/`--msi`/`--dmg`. |

<Callout title="Extra args after --output are forwarded to the game, not to mach">
`mach bundle`'s own flags (`--package-name`, `--package-version`, `--msi`, ...) are for
naming/shaping the *installer*. Anything else on the command line is written into the
bundle's `launch.json` and handed to the running game at launch as real CLI args — the two
are validated against each other so one can't accidentally leak into the other.
</Callout>
