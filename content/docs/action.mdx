<Accordion title="New to GitHub Actions?" id="what-is-github-actions">

**GitHub Actions** is GitHub's built-in automation system: a `.yml` *workflow* file describes
a sequence of steps GitHub runs for you, on GitHub's own servers, whenever something happens
in your repo (a push, a tag, a manual trigger) — nothing runs on your own machine. Workflow
files live at `.github/workflows/*.yml` in your repo; GitHub picks up anything there
automatically, no separate registration step needed.

An *action* like `roves-action` is a single reusable step you drop into one of those
workflows with `uses: ...`, the same way `actions/checkout` or `actions/setup-node` already
are in the examples below.

</Accordion>

</Accordions>

[`roves-action`](https://github.com/DRincs-Productions/roves-action) is a GitHub Action — a
reusable, automated step for the kind of workflow described in the accordion above. It lets
you delegate what you'd otherwise do by hand with the
<DynamicLink href="/docs/shell">Shell</DynamicLink> or
<DynamicLink href="/docs/packmaster">Packmaster</DynamicLink> to an online job instead — one
GitHub starts for you on a Windows, macOS, or Linux machine on demand, to generate your
package without you sitting in front of any of them.

By default it packages your already-built web content into a native bundle the same way
<DynamicLink href="/docs/packmaster">Packmaster</DynamicLink> does: it downloads the same
prebuilt `roves_shell_<platform>[_steam].zip` release asset Packmaster itself uses and packs
your content into it — nothing gets compiled, so there's no native toolchain to install at
all. See [Advanced mode](#advanced-mode) below for the opt-in, slower path that compiles the
engine from source instead.

The big advantage over Packmaster either way: this runs on whichever operating system you
need — Windows, macOS, or Linux — as a GitHub-hosted job, without you ever installing
anything on your own machine. You only ever provide your already-built web content.

<Accordions>

<Accordion title="Prerequisites" id="prerequisites">

A GitHub account, and your game's project in a GitHub repository — that's it. The repository
doesn't need to be public: GitHub Actions runs on private repos too, it just draws from your
account's own included Actions minutes there (public repos get unlimited minutes on the
standard runners this action uses; private repos don't).

</Accordion>

</Accordions>

## Base mode (the default)

The default output on every platform, no install step. This action doesn't build your
game's own web content for you — it doesn't know or care what produced it — so a step that
does that has to run first, as in the `build game content` step below.

A full, realistic shape: triggered by pushing a version tag, one job per desktop platform
via a matrix (`windows-latest`/`macos-latest`/`ubuntu-latest` — desktop is all that actually
works today, there's no cross-compiling for consoles here, see
<DynamicLink href="/docs/shell">the Shell section</DynamicLink> for what `mach` itself
supports), and a real GitHub Release created first and uploaded to at the end — the same
create-then-upload shape this repo's own release workflows use:

```yml
name: Release

on:
  push:
    tags:
      - 'v*.*.*'

jobs:
  create-release:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - name: create the GitHub Release for this tag
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh release create "${{ github.ref_name }}" --title "My Game ${{ github.ref_name }}"

  build-and-publish:
    needs: create-release
    permissions:
      contents: write
    strategy:
      fail-fast: false
      matrix:
        include:
          - platform: windows-latest
            os_name: windows
          - platform: macos-latest
            os_name: macos
          - platform: ubuntu-latest
            os_name: linux

    runs-on: ${{ matrix.platform }}
    steps:
      - uses: actions/checkout@v4

      - name: build game content
        uses: actions/setup-node@v4
        with:
          node-version: '22'
      - run: npm install && npm run build

      - name: build & bundle with Roves
        id: roves
        uses: DRincs-Productions/roves-action@v1
        with:
          content-dir: dist
          artifact-name: my-game_${{ matrix.os_name }}

      - name: upload to the release
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh release upload "${{ github.ref_name }}" "${{ steps.roves.outputs.archive-path }}"
```

`create-release` runs once, before the matrix starts (`build-and-publish`'s `needs:` waits
for it) — otherwise 3 concurrent jobs would race to create the same release. Both jobs need
`contents: write`: one to create the release, the other to upload to it.

The only required `roves-action` input is `content-dir`; everything else defaults sensibly.
Every `mach build`/`mach bundle` input is tagged `[servo]` (plain upstream Servo — see
<DynamicLink href="/docs/shell">the Shell section</DynamicLink> for what each one does) or
`[roves]` (added by `mach bundle`, which doesn't exist upstream at all) in the action's own
`action.yml`/README — the flags themselves are exactly the ones documented there, this
action is a near 1:1 forwarding layer over them. `features: 'steam'` gets you the
<DynamicLink href="/docs/integrations/steam">Steam bridge</DynamicLink> either way: in the
default base mode it selects the separately-published Steam-enabled shell asset instead of
compiling anything, while with `advanced-mode: 'true'` it's forwarded straight to `mach
build --features steam` as usual.

### Outputs

| Name | Description |
| --- | --- |
| `bundle-dir` | Absolute path to the unzipped bundle folder (named `artifact-name`) |
| `archive-path` | Absolute path to `<artifact-name>.zip` |

## Distributing installers

Each platform also has one installable input, gated to its own OS — setting one on the
wrong runner is silently ignored, so a single input set (even with more than one turned on)
can stay the same across a matrix:

| Platform (`runner.os`) | Installable input | Produces |
| --- | --- | --- |
| `Windows` | `msi: 'true'` | A real `.msi` (needs WiX's `candle`/`light` on `PATH` — this action adds it for you on `windows-latest`) |
| `macOS` | `dmg: 'true'` | `play.app` wrapped in a `.dmg` |
| `Linux` | `deb: 'true'` | A real `.deb` |

The same matrix shape as [Base mode](#base-mode-the-default) above, with one installable
input added per platform instead:

```yml
name: Release

on:
  push:
    tags:
      - 'v*.*.*'

jobs:
  create-release:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - name: create the GitHub Release for this tag
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh release create "${{ github.ref_name }}" --title "My Game ${{ github.ref_name }}"

  build-and-publish:
    needs: create-release
    permissions:
      contents: write
    strategy:
      fail-fast: false
      matrix:
        include:
          - platform: windows-latest
            os_name: windows
            msi: 'true'
          - platform: macos-latest
            os_name: macos
            dmg: 'true'
          - platform: ubuntu-latest
            os_name: linux
            deb: 'true'

    runs-on: ${{ matrix.platform }}
    steps:
      - uses: actions/checkout@v4

      - name: build game content
        uses: actions/setup-node@v4
        with:
          node-version: '22'
      - run: npm install && npm run build

      - name: build & bundle with Roves
        id: roves
        uses: DRincs-Productions/roves-action@v1
        with:
          content-dir: dist
          artifact-name: my-game_${{ matrix.os_name }}
          msi: ${{ matrix.msi || 'false' }}
          dmg: ${{ matrix.dmg || 'false' }}
          deb: ${{ matrix.deb || 'false' }}
          package-name: my-game
          package-version: ${{ github.ref_name }}

      - name: upload to the release
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh release upload "${{ github.ref_name }}" "${{ steps.roves.outputs.archive-path }}"
```

`package-name`/`package-version` name and version whichever installable format you asked
for — ignored entirely when none of `deb`/`msi`/`dmg` are set. See
<DynamicLink href="/docs/shell">the Shell section</DynamicLink> for what each format actually
wraps under the hood.

## Advanced mode

Setting `advanced-mode: 'true'` switches to checking out the engine source at `roves-ref`
and running `mach bootstrap` + `mach build` + `mach bundle` against it, mirroring the engine
repo's own `test.yml`, instead of downloading a prebuilt shell — slower, but every input
that exists purely to control *how the engine compiles* (cross-compile target,
`media-stack`, sanitizers, a custom `icon-png`/`icon-ico`, and a few others) becomes
available, since this is the only path that actually compiles anything. Setting one of those
inputs while `advanced-mode` is left at its default fails the run with a clear error instead
of silently ignoring it. See the action's own README for the full list and a working
advanced-mode example.
