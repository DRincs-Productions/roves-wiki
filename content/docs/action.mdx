<Accordions>

<Accordion title="New to GitHub Actions?" id="what-is-github-actions">

**GitHub Actions** is GitHub's built-in automation system: a `.yml` *workflow* file describes
a sequence of steps GitHub runs for you, on GitHub's own servers, whenever something happens
in your repo (a push, a tag, a manual trigger) — nothing runs on your own machine. Workflow
files live at `.github/workflows/*.yml` in your repo; GitHub picks up anything there
automatically, no separate registration step needed.

An *action* like `roves-action` is a single reusable step you drop into one of those
workflows with `uses: ...`, the same way `actions/checkout` or `actions/setup-node` already
are in the examples below.

</Accordion>

</Accordions>

[`roves-action`](https://github.com/DRincs-Productions/roves-action) is a GitHub Action — a
reusable, automated step for the kind of workflow described in the accordion above. It lets
you delegate what you'd otherwise do by hand with the
<DynamicLink href="/docs/shell">Shell</DynamicLink> or
<DynamicLink href="/docs/packmaster">Packmaster</DynamicLink> to an online job instead — one
GitHub starts for you on a Windows, macOS, or Linux machine on demand, to generate your
package without you sitting in front of any of them.

By default it packages your already-built web content into a native bundle the same way
<DynamicLink href="/docs/packmaster">Packmaster</DynamicLink> does: it downloads the same
prebuilt `roves_shell_<platform>[_steam].zip` release asset Packmaster itself uses and packs
your content into it — nothing gets compiled, so there's no native toolchain to install at
all. See [Advanced mode](#advanced-mode) below for the opt-in, slower path that compiles the
engine from source instead.

The big advantage over Packmaster either way: this runs on whichever operating system you
need — Windows, macOS, or Linux — as a GitHub-hosted job, without you ever installing
anything on your own machine. You only ever provide your already-built web content.

<Accordions>

<Accordion title="Prerequisites" id="prerequisites">

A GitHub account, and your game's project in a GitHub repository — that's it. The repository
doesn't need to be public: GitHub Actions runs on private repos too, it just draws from your
account's own included Actions minutes there (public repos get unlimited minutes on the
standard runners this action uses; private repos don't).

</Accordion>

</Accordions>

## Base mode (the default)

Add [`DRincs-Productions/roves-action@v1`](https://github.com/DRincs-Productions/roves-action)
as a step in your own workflow — this is the action that actually generates your game. Its
only required input is `content-dir`, pointing at your already-built web content; every other input
(see [Inputs](#inputs) below) defaults sensibly, and by default it produces a portable,
no-install-step game for whichever platform the job runs on.

Triggered by pushing a version tag, a matrix starts one job per desktop platform
(`windows-latest`/`macos-latest`/`ubuntu-latest`) in parallel, each running this action once
and uploading its own output to a real GitHub Release created first — the same
create-then-upload shape this repo's own release workflows use:

```yml
name: Release

on:
  push:
    tags:
      - 'v*'

jobs:
  create-release:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - name: create the GitHub Release for this tag
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh release create "${{ github.ref_name }}" --title "My Game ${{ github.ref_name }}"

  build-and-publish:
    needs: create-release
    permissions:
      contents: write
    strategy:
      fail-fast: false
      matrix:
        include:
          - platform: windows-latest
            os_name: windows
          - platform: macos-latest
            os_name: macos
          - platform: ubuntu-latest
            os_name: linux

    runs-on: ${{ matrix.platform }}
    steps:
      - uses: actions/checkout@v4

      - name: build game content
        uses: actions/setup-node@v4
        with:
          node-version: '22'
      - run: npm install && npm run build

      - name: build & bundle with Roves
        id: roves
        uses: DRincs-Productions/roves-action@v1
        with:
          content-dir: dist
          artifact-name: my-game_${{ matrix.os_name }}

      - name: upload to the release
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh release upload "${{ github.ref_name }}" "${{ steps.roves.outputs.archive-path }}"
```

### Inputs

| Name | Description |
| --- | --- |
| `content-dir` | **Required.** Path to your already-built web content (e.g. a Vite/webpack `dist/` folder). |
| `artifact-name` | Base name for the output folder and zip (default `roves-game`). |
| `features` | `''` (default) or `'steam'`, for the <DynamicLink href="/docs/integrations/steam">Steam bridge</DynamicLink>. |
| `deb` / `msi` / `dmg`, `package-name`, `package-version` | Build an installer instead of a portable bundle — see [Distributing installers](#distributing-installers) below. |
| `html-file` | Entry HTML file, relative to `content-dir` (default `index.html`). |
| `window-size` | Initial window size, e.g. `1280x720` (the default). |
| `output` | Where the bundle gets written, relative to your repo root. Usually left unset — the action picks its own path and exposes it via `bundle-dir`/`archive-path` regardless. |
| `diagnostic-script` | Ship a `diagnose.bat`/`diagnose.sh` alongside the bundle (portable/`msi`/`dmg`, not `deb`) that launches the game from a console and prints its exit code plus `roves.log` — for testers to run when a build appears to do nothing. Off by default. |
| `bundle-params` | Extra launch arguments baked into the bundle, passed to the game every time it starts. |

### Custom game icon

| Name | Description |
| --- | --- |
| `icon-png` | Path to a window/taskbar icon (PNG). Works in either mode — `mach bundle` applies it after packaging, no compile needed. Not supported on macOS yet (its own Dock/app icon has no runtime override). |
| `icon-ico` | Path to a Windows `.exe` icon (multi-size `.ico`). Windows only. Patches the bundled `play.exe`'s icon resource in place via `rcedit`, also no compile needed. |

Leave both unset and Roves auto-detects an `icon.png`/`icon.ico` sitting directly in
`content-dir` before falling back to its own default branding — many bundlers already emit
one there for their own PWA manifest, so a game that already has one gets its own icon for
free. An explicit `icon-png`/`icon-ico` above always wins over this.

### Content packing

How your content gets packed into the bundle — see
<DynamicLink href="/docs/integrations/content-packing">Content packing</DynamicLink> for the
full design (why, the boot-set/lazy-extraction split, the archive layout). These inputs are
a direct passthrough to the matching `mach bundle` flags (see
<DynamicLink href="/docs/shell#content-packing">the Shell page's own table</DynamicLink>):

| Name | Description |
| --- | --- |
| `content-compress` | `auto` (default): pack into a handful of tar+zstd archives. `none`: copy in as loose, individually browsable files. |
| `content-compression-level` | zstd level for `content-compress: 'auto'` (default `1`). Low by default — speed over ratio. |
| `content-max-pack-size` | Split archives so none exceeds this size (default `500M`). |
| `content-exclude` | Globs (one per line for more than one). Leave matching files as loose, uncompressed files (e.g. a save-data folder that shouldn't sit inside a read-only archive). |
| `content-boot-include` | Globs (one per line for more than one). Extra files eagerly extracted at boot, beyond the html file and whatever it directly references. |

### Outputs

| Name | Description |
| --- | --- |
| `bundle-dir` | Absolute path to the unzipped bundle folder (named `artifact-name`) |
| `archive-path` | Absolute path to `<artifact-name>.zip` |

## Distributing installers

Each platform also has one installable input, gated to its own OS — setting one on the
wrong runner is silently ignored, so a single input set (even with more than one turned on)
can stay the same across a matrix:

| Platform (`runner.os`) | Installable input | Produces |
| --- | --- | --- |
| `Windows` | `msi: 'true'` | A real `.msi` (needs WiX's `candle`/`light` on `PATH` — this action adds it for you on `windows-latest`) |
| `macOS` | `dmg: 'true'` | `play.app` wrapped in a `.dmg` |
| `Linux` | `deb: 'true'` | A real `.deb` |

The same matrix shape as [Base mode](#base-mode-the-default) above, with one installable
input added per platform instead:

```yml
name: Release

on:
  push:
    tags:
      - 'v*.*.*'

jobs:
  create-release:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - name: create the GitHub Release for this tag
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh release create "${{ github.ref_name }}" --title "My Game ${{ github.ref_name }}"

  build-and-publish:
    needs: create-release
    permissions:
      contents: write
    strategy:
      fail-fast: false
      matrix:
        include:
          - platform: windows-latest
            os_name: windows
            msi: 'true'
          - platform: macos-latest
            os_name: macos
            dmg: 'true'
          - platform: ubuntu-latest
            os_name: linux
            deb: 'true'

    runs-on: ${{ matrix.platform }}
    steps:
      - uses: actions/checkout@v4

      - name: build game content
        uses: actions/setup-node@v4
        with:
          node-version: '22'
      - run: npm install && npm run build

      - name: build & bundle with Roves
        id: roves
        uses: DRincs-Productions/roves-action@v1
        with:
          content-dir: dist
          artifact-name: my-game_${{ matrix.os_name }}
          msi: ${{ matrix.msi || 'false' }}
          dmg: ${{ matrix.dmg || 'false' }}
          deb: ${{ matrix.deb || 'false' }}
          package-name: my-game
          package-version: ${{ github.ref_name }}

      - name: upload to the release
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh release upload "${{ github.ref_name }}" "${{ steps.roves.outputs.archive-path }}"
```

`package-name`/`package-version` name and version whichever installable format you asked
for — ignored entirely when none of `deb`/`msi`/`dmg` are set. See
<DynamicLink href="/docs/shell">the Shell section</DynamicLink> for what each format actually
wraps under the hood.

## Advanced mode

Setting `advanced-mode: 'true'` kicks off a much slower, longer-running job: instead of using
Roves' already-built files — ready to be packed straight into your game's bundle, the default
— it compiles them itself from scratch, on the spot. That trades speed for a lot more control
over how the engine gets built, entirely at your own risk.

:::warning

Setting any of the inputs below while `advanced-mode` is left at its default (`'false'`) fails the run with a clear error
instead of silently ignoring it.

:::

<Accordions>

<Accordion title="Inputs" id="advanced-mode-inputs">

| Name | Description |
| --- | --- |
| `bootstrap` | Install the native build dependencies the compile step needs (default `true`). Set to `false` only if you already installed them yourself in an earlier step. |
| `release` | Build with full optimizations. |
| `dev` | Debug build (the default if `release`, `production`, and `profile` are all unset). |
| `production` | Release build without debug assertions. |
| `profile` | Build with a custom named profile instead of `dev`/`release`/`production`. |
| `target` | Cross-compile for a different target triple. Leave unset for a normal desktop build. |
| `features` | Extra engine features to enable, space-separated (e.g. `steam`). |
| `media-stack` | Which media backend to build with: `gstreamer` for real audio/video, or `dummy` to skip it and avoid installing GStreamer at all (no audio/video playback). |
| `jobs` | Limit how many build jobs run in parallel. |
| `with-asan` / `with-tsan` | Build with AddressSanitizer / ThreadSanitizer, for tracking down memory or threading bugs. |
| `with-debug-assertions` | Keep debug assertions even in an otherwise optimized build. |
| `debug-mozjs` | Build the JavaScript engine with debug assertions. |
| `with-frame-pointer` | Keep frame pointers in the build (helps diagnose hangs). |
| `use-crown` | Enable the engine's own memory-safety lint tool during the build. |
| `coverage` | Build with code-coverage instrumentation. |
| `android` / `ohos` | Build for Android / OpenHarmony. Not currently a supported Roves platform. |
| `win-arm64` | Build for Windows on Arm64 instead of x64. |
| `flavor` | Product flavor name — only relevant to Android/OpenHarmony packaging. |
| `verbose` / `very-verbose` | Print more detail while building. |
| `no-package` | Android only: skip packaging into a `.apk` after building. |
| `build-params` | Any extra arguments to pass straight through to the build step, space-separated. |
| `bin` | Point at a specific already-built binary instead of letting the action find the one it just built. |
| `nightly` | Use a dated nightly build instead of the one just compiled. |

</Accordion>

</Accordions>

```yml
- name: build & bundle with Roves (advanced mode)
  uses: DRincs-Productions/roves-action@v1
  with:
    content-dir: dist
    advanced-mode: 'true'
    media-stack: dummy
```
